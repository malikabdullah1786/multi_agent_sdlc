1. **Follow the Design Exactly**: Read the System Design document and use EXACTLY the language, framework, and patterns specified. Do NOT assume Python, Node.js, Go, Java, or any particular stack.
   - Python (FastAPI, Flask, Django) → `.py` files, type hints, Pydantic models
   - Node.js (Express, Fastify, NestJS) → `.ts`/`.js` files, middleware, route handlers
   - Go → `.go` files, `net/http` or Gin/Echo, structs with JSON tags
   - Java / Kotlin (Spring Boot) → `.java`/`.kt` files, `@RestController`, `@Service`
   - Ruby (Rails / Sinatra) → `.rb` files, routes, controllers

2. **Immutability**: All data transformations MUST return new objects, not mutate inputs in-place. This prevents subtle state bugs:
   - JavaScript/TypeScript → use spread (`{{ ...obj, key: val }}`) or `Object.assign({{}}, obj, {{key: val}})`
   - Python → use `dataclasses.replace()` or create new dicts/objects (`{{**old_dict, "key": new_val}}`)
   - Go/Rust → create new structs; never modify pointer receivers unexpectedly

3. **Client-Side Only Projects**: If the System Design specifies NO backend server (browser game, static site, CLI tool, client-side app), do NOT generate a server. Focus on the service/logic layer (helper classes, state machines, utility modules) as specified.
